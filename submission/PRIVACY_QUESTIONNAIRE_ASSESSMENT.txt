PAWVERIO — AMAZON PRIVACY QUESTIONNAIRE ASSESSMENT
Assessment date: 2026-11-04. Status: DRAFT; technical evidence and recommended answers, not a legal compliance certification.
Scope: current Android source, native Amazon Appstore SDK 3.0.9, and primary public documentation. No account details, secrets, live purchaser records, browser actions, or runtime network inspection were used. Parent must bind this assessment to the exact signed APK before submission.

DECISION
Recommended app-level answer: YES, the app handles user-associated data through optional speech and Amazon purchasing, in addition to local records. An overall NO is not defensible merely because Pawverio has no account server, advertising SDK, or INTERNET permission. Service processes can communicate independently of this APK.

AMAZON RULES THAT CONTROL THE MAPPING
Amazon includes third-party SDK/service-provider collection. Its transfer definition has exclusions for processors acting on the developer's behalf and clearly expected/disclosed user-initiated sharing; those exclusions must be established, not assumed. Its categories include User IDs, Purchase history, utterances, Photos, Files and docs, Contacts, Other user-generated content and Diagnostics. The reviewed pages do not explicitly establish a blanket exemption for all on-device processing. Do not silently substitute another store's definitions. [1][2]

VERIFIED IMPLEMENTATION AND PROVISIONAL ANSWERS
The labels below separate code facts from questionnaire interpretation. YES-DRAFT is a cautious proposed answer, not proof of off-device transmission. If the live form expressly excludes processing wholly on-device, the local-only collection rows can instead be NO under that exact definition; retain the local processing in the privacy notice.

A. Pet records and human-entered notes/assignments
Facts: Room stores pets, routines, health records, weights, care history and household members locally. Settings hold household instructions and emergency contact text. Human household names and contact details can be entered manually. No contact-book, phone-log, location, camera, ad-ID or cloud-sync integration was found in first-party source/manifest.
Mapping: Other user-generated content; Name/Contacts when human household/contact fields are used. COLLECTED: YES-DRAFT under the broad local-handling reading; local-only exclusion requires form/support clarification. TRANSFER: NO for ordinary storage; separate speech/export paths below. Purpose: App functionality. Pet weight/vaccination data is not designed to collect a HUMAN user's Health & Biometrics/Fitness data; do not mark human medical categories solely because the product contains animal records.
Phone number/email/address: no dedicated account fields or device-address-book reading. Manually entered contact details may contain them; evaluate the live form's contact-category instructions rather than automatically asserting every User Info subtype is collected.

B. Photographs and attached records
Facts: users select files through Android document pickers; selected items are copied into app-private attachment storage. No automatic upload path was found. Android backup is disabled in the application manifest. Local PDF/text/JSON exports and records-only encrypted backup are user-selected SAF destinations; an external/cloud document provider can receive the chosen output. Backup excludes photos/documents.
Mapping: Photos, Files and docs, and related Other user-generated content. COLLECTED: same local-only qualification as A (YES-DRAFT if broad handling). TRANSFER: NO for local import/storage. User-initiated export may fit Amazon's expected-action exclusion only because the app shows an explicit sensitive-export confirmation and the user chooses the destination; a cloud destination is not evidence that Pawverio silently uploads everything. Purpose: App functionality. Do not claim Pawverio can delete already exported copies.

C. Microphone commands and TTS text
Facts: VoiceController uses installed SpeechRecognizer after push-to-talk/permission; no continuous/background listening or raw recording persistence is implemented. Recognition is NOT restricted to an offline provider. Recognized text is previewed in app state; no developer endpoint was found. TextToSpeech.speak sends supplied text to the installed synthesis engine, including pet names/care-task text when the user requests a readout. Spoken feedback can be disabled. The UI discloses installed speech-service processing. First-party code cannot establish each provider's retention, cloud routing, or secondary uses. On tested KFTRWI recognition was unavailable; that does not remove the feature from other compatible devices. [4]
Mapping: Voice or sound recordings: COLLECTED YES-DRAFT for optional recognition. Other user-generated content, and Names/Contacts if included in read-aloud text: COLLECTED YES-DRAFT for provider handling. Purpose: App functionality. TRANSFER: conditional, not blanket NO. NO is supportable only if the actual provider relationship/disclosed user-request meets Amazon's exclusion; otherwise YES. Provider-specific off-device collection, retention, identifiers and independent-use purposes remain UNKNOWN. TTS engine capability tests do not establish network privacy.

D. Amazon purchasing and entitlement cache
Facts: connect() invokes getUserData/getProductData when a nonempty app-specific public-key asset exists, and successful user-data retrieval triggers restore. This can happen at app startup, not only after pressing Buy. The app receives an app-specific Amazon user ID, purchase updates/receipts and store prices. It persists Amazon user ID plus a premium boolean in private SharedPreferences; receipt IDs/cancellation facts are held in an in-memory ledger. Purchase and fulfillment commands communicate with Amazon Appstore. No developer RVS server is implemented. Amazon's documentation identifies user-specific ID and purchase-history callbacks. [3]
Mapping: User IDs and Purchase history: COLLECTED YES. Purposes: App functionality; Fraud Prevention, Security & Compliance for identity/receipt/entitlement validation. TRANSFER: conservative YES-DRAFT for Amazon transaction processing unless a documented service-provider exclusion is established. Do not rely solely on user-initiated-purchase exclusion: startup identity/restore processing is automatic. The fact that Amazon originally supplied the identifier does not justify saying the app never handles it. User payment info/card details: NO for first-party code; payment credentials are entered in Amazon's own flow and Pawverio does not read them. This is separate from purchase history. [1][3]

E. SDK diagnostics, device identifiers and other analytics
Verified static SDK evidence: the pinned Maven JAR contains com.amazon.device.iap.internal.util.MetricsHelper. Its submitReceiptVerificationFailureMetrics packages stringToSign/signature; submitJsonParsingExceptionMetrics packages jsonString/description; submitExceptionMetrics packages exceptionMessage/description. submitMetric constructs com.amazon.device.iap.internal.a.k.a, compiled from SubmitMetricCommand.java, with command name submit_metric, metricName and metricAttributes, then invokes its task. ReceiptHelper contains actual call sites for receipt-verification-failure metrics. License/receipt classes also contain deviceId/DeviceId fields. This is executable diagnostic machinery, not evidence of an advertising SDK.
Mapping: Diagnostics: COLLECTED YES-DRAFT, not an unsupported global NO. Purposes supported by the calling context: App functionality and security/fraud prevention for receipt failures. Analytics is also a plausible purpose for diagnostic/debugging metrics under Amazon's taxonomy; do not certify Analytics=NO without vendor confirmation. Actual Amazon secondary uses and whether metrics are user-associated, anonymized, retained or forwarded are UNKNOWN; obtain Amazon's SDK data-disclosure guidance. TRANSFER YES-DRAFT unless an applicable exclusion is confirmed. Device or other IDs: POSSIBLE/UNRESOLVED; identifier fields exist but runtime acquisition/transmission/association was not traced exhaustively. Do not assert either global NO or unconditional YES from field names alone. Crash logs/app interactions/installed-app inventory: no first-party uploader/tracker was found; exact SDK/platform collection remains UNKNOWN. Do not treat technical exception metrics as proof that every crash-log category is collected.
No first-party advertising, marketing, data sale, behavioral profiling, or unrelated analytics implementation was found. Do not select those purposes merely to fill a required field. Do not certify that all SDK/platform parties have no independent purposes without vendor evidence.

DELETION / RETENTION / RELEASE NOTES
The in-app data-delete flow clears care records, attachments, private household contact/instructions and reminder work. It does not clear the separate Amazon entitlement cache, erase Amazon transaction records, remove speech-provider records, or revoke user-created exports. Thus avoid a promise that the button deletes every item everywhere. No Pawverio account is created; an Amazon store account is a separate service. Owner must describe retained entitlement data and external-service deletion routes accurately and provide the required public policy/deletion information. [5]

NARROW SDK REACHABILITY ADDENDUM — 2026-11-04
This supersedes the earlier 'mere deviceId field names' uncertainty for the paths described below. Static reachability is verified in the actual 3.0.9 JAR; real transaction payloads, transmissions and vendor retention were not observed.

1. Store-supplied DeviceId is consumed by the implemented restore path.
PurchasingService.getPurchaseUpdates(boolean) -> com.amazon.device.iap.internal.d.a(boolean) [PurchasingManager] -> production com.amazon.device.iap.internal.a.d.a(RequestId,boolean) [KiwiRequestHandler] -> internal.a.c.a [GetPurchaseUpdatesRequest] -> internal.a.c.d [PurchaseUpdatesCommandV2]. The command parses receipt JSON and invokes internal.util.c.a(JSONObject,String,String) [ReceiptHelper]. That dispatches according to receipt format; its modern e(JSONObject,String,String) branch reads optString("DeviceId") at bytecode offset 3. The value is inserted into the signed receipt string at offsets 280–283, alongside user ID, product type, SKU, receipt ID and transaction dates. Signature verification uses that string. On verification failure, offsets 403–408 pass request ID, that string and the signature to MetricsHelper.submitReceiptVerificationFailureMetrics. The helper packages stringToSign/signature into SubmitMetricCommand (internal.a.k.a), command name submit_metric, metricName and metricAttributes.
This is reachable IAP receipt handling, not a conclusion drawn from unrelated DRM/license classes. DeviceId is obtained FROM an Amazon-supplied receipt, not proven to be read directly from Android's serial/advertising-ID APIs. Legacy receipts need not contain it. ReceiptHelper does not expose DeviceId on the app's public Receipt model. Successful receipts still consume the value for verification; the identified failure path additionally includes it in a diagnostic command. Whether that command completes or the store forwards it off-device is runtime/vendor-dependent.
No separate direct device-ID acquisition was established specifically in getUserData/getProductData. Do not turn that narrower finding into an all-SDK No.

2. Routine metrics are reachable without deliberately invoking an error.
PurchasingService.registerListener calls AppstoreSDK initialization (com.amazon.android.a), whose initialization method b(Application), offsets 200–227, initializes MetricManager and AmazonAppstoreManager. PurchasingManager methods invoked by getUserData, getProductData and getPurchaseUpdates queue IAP_GUD, IAP_GPD and IAP_GPU respectively, with request IDs and System.currentTimeMillis timestamps. This is direct call-site evidence, not a dormant method-name match.
MetricManager (com.amazon.android.a.b.b) generates a process-session UUID. Its bundle builder adds metric name, timestamp, sessionId and requestId; optional receipt IDs and fulfillment status can also be included. A conditional flush checks ServiceConfigManager.d(); unsupported configurations discard the queue. Supported flushes route the iapMetrics bundle through AmazonAppstoreManager -> production com.amazon.android.a.a.b [KiwiRequestHandler] -> com.amazon.android.a.a.a.b [request] -> com.amazon.android.a.a.a.a [SyncMetricsCommand], command sync_metrics with metricBatch. SDK internal version strings differ from Maven version naming; the artifact audited remains the pinned Maven 3.0.9 JAR.
Consequently, absence of a first-party analytics SDK or app INTERNET permission does NOT establish absence of SDK diagnostics or app/API-use telemetry. These metrics contain request/session/transaction association rather than being proven anonymous aggregates. Actual vendor association, remote retention and secondary uses remain unresolved.

3. Implication for the saved questionnaire.
User IDs and Purchase history have direct positive evidence. Device or other IDs now has a concrete conditional IAP receipt-handling path; a cautious YES-DRAFT is supported for the DeviceId/session identifier processing that can occur, rather than the previous field-name-only inference. Suggested purposes remain app functionality/security for receipt verification; diagnostic/use telemetry may also require Analytics. Do not certify the latter as No without vendor clarification.
Third-party-transfer exclusions still require a documented basis: routine startup identity/restore/telemetry is not all explained by a customer pressing Buy. Saving a draft with only User IDs selected must not be described as complete or verified if unselected rows become No. Preserve these unresolved classifications and obtain vendor/form guidance before final certification.
